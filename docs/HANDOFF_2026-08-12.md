# 接手提示词 — OpenCodex v2.2.3 之后

把下面整段贴给本项目下的新 Claude 会话。

我在 `D:\coding\Development\tools\opencodex-fork` 维护 OpenCodex —— 一个 Windows 11 上让 Codex Desktop 使用第三方模型的网关。当前 `main` 分支已发布 v2.2.3。

请先读 `docs/AUDIT_REPORT_v2.2.3_2026-08-12.md`。那是 GPT-5.6 Sol 对 v2.2.3 做的严格审阅 + 端到端测试报告,我已逐条抽查过高优先级项,**报告的结论是准确的**。请按报告末尾的顺序修复,一项一个 commit,每个 commit 都要有对应测试。

## 先做这四项

1. **P1-2 第三方 Responses 没有流式**(最严重)。`src_v2/server/router.ts:436` 先 `collectThirdPartyResponsesBody()` 收完整条 SSE 流,`res.writeHead()` 到 470 行才执行 —— 首字节延迟等于整次生成时间。缓冲只为 438 行的子代理续答循环服务,而它仅在 `subagentDispatcher && !isSubagentRequest` 时可能触发。无内部编排时应直接流式转发。必须加"首个 SSE 事件先于上游完成到达"的时序测试。
2. **P1-3 `opencode-go-pro` 不存在**(`gateway.ts:2436`)。新用户按预设保存即得到必然失败的模型。同时 OpenCode Go 部分模型走 `/chat/completions`、部分走 `/v1/messages`,当前单一 Base URL 表达不了。
3. **P2-1 `Start-OpenCodex.cmd` 写死 `OPENCODEX_PORT=8765`**(`scripts/package-windows.mjs`),而网关把该变量存在视为"用户显式指定"、拒绝顺延 —— 直接推翻 README 承诺的自动换端口。
4. **P1-1 上游入口未强制令牌**。当初不强制的理由是"原生透传可能不带 bearer",但 2.2.0 起 bridge 转发时已附带 admin token,该理由已失效。README 声称"所有可触达上游的入口都需要网关令牌",代码没做到。改为 `isUpstreamReachingPath()` 一律 `requireAdmin()`,并加无令牌的负向 E2E。

## 这个项目会咬人的地方

- **测试隔离只做了一半。** 之前修过一轮(构造函数注入 `DesktopController` + `OPENCODEX_TEST_MODE=1` 兜底),注册表不会再被碰,但报告指出 `port_conflict.test.mjs` 和 `gateway_discovery.test.mjs` 仍会读写真实 `~/.opencodex` 和固定端口。**跑 `npm test` 前先确认这一点**,必要时先补隔离。
- **PowerShell 编码。** `config.toml` 是无 BOM UTF-8,Windows PowerShell 5.1 的 `Get-Content`/`Set-Content` 不指定编码时按系统代码页(中文机器是 GBK)处理,会**不可逆地**破坏非 ASCII 内容。v2.2.3 就是修这个。任何读写用户文件的地方都必须显式 UTF-8。
- **`.cmd` 必须 CRLF。** 已有 `.gitattributes` + 打包时转换 + 测试守着,别绕过。
- **用户的 Codex 配置里有中文项目路径**,任何改 `config.toml` 的改动都要用含中文路径的 fixture 测。

## 验证要求(这是重点)

这个项目上一轮出过多次事故,**全部是同一个原因:确认了"我想让它发生的事发生了",没确认"我不想发生的事没发生"**。具体教训:

- 改完 `config.toml` 相关逻辑,不能只查"托管块删掉了",必须查**其余部分逐字节未变**
- 不要拿自己构造的反例验证自己的假设(曾写测试断言"Codex 不发浏览器头",而测试本身就没发那些头)
- 文档/注释描述的是意图,不是行为 —— 恢复脚本的注释写得很好,而它从加入仓库起就没运行成功过
- 消除"文档与默认值矛盾"时,先问哪一边是对的(曾把 oracle 默认值改成关闭以迁就文档,结果第三方子代理整个不可用)

改动部署到真机验证时:安装目录是 `D:\coding\Development\tools\OpenCodex`(**固定路径,不要带版本号,不要新建目录**),流程是停进程 → 覆盖内容 → 启动 `OpenCodex.exe --background` → 调 `/api/restart-codex` 拉起 Desktop。验证点:`/health` 版本、`CODEX_CLI_PATH` 指向、`config.toml` 的 FFFD 数与坏表头数、`trust_level` 计数(应为 69)、服务商 key 状态。

## 发布流程

版本号在 4 处:`package.json`、`native/windows-bridge-launcher/Cargo.toml`、`native/windows-launcher/Cargo.toml`、`src_v2/server/gateway.ts` 的 `/health`。`test/release_version.test.mjs` 以 package.json 为唯一来源校验一致性。

```
npm run build && node scripts/run-tests.mjs && node scripts/package-windows.mjs
git push origin HEAD:main && git push origin vX.Y.Z
gh release create vX.Y.Z build/OpenCodex-X.Y.Z-win-x64.zip --notes-file <changelog 节选>
```

主线只有 `main`(`master` 已删除)。CHANGELOG 要如实写,包括自己改错又反转的决定。
